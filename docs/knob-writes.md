# ノブスロットへの書き込みについて

対象: K1-L / K1-C / K1-R（スロット 13〜15）、K2-L / K2-C / K2-R（16〜18）への
キー／メディア／マウス割り当ての書き込み。

## 前提（調査結果）

- ノブスロットは通常キーと**同じレポート形式**で書き込む。レポート先頭バイトが
  スロット番号、という点だけが違う。ベンダーアプリ（MINI KeyBoard.exe）を
  デコンパイルして復元した公開プロトコル資料でも、RSoft MacroPad の
  アクション番号変換（ノブ 23〜31 → ワイヤ上の 13〜21）でも、ノブ専用の
  コマンドやアドレス空間は存在しない。
- したがってアプリ側のバイト列にノブ固有の誤りは無い。既知の動作する実装
  （バイト一致が検証された macropad.py）との唯一の機能差は**フレーム間隔**で、
  同実装は全フレームの後に 10ms の待ちを入れている（MCU がフラッシュへ
  保存する時間を与えるため）。

## 実装した対策

1. **フレーム pacing**: 書き込みシーケンスの各フレーム送信後に待ちを入れる。
   通常フレーム後は 10ms、保存（コミット）フレーム `0xAA …` の後は 60ms
   （`protocol::frame_delay_after_ms`）。プリセット一括適用やボタン設定の
   書き戻しのように書き込みが連続する場合でも、MCU のフラッシュ保存中に
   次のフレームが届いて黙って落ちることを防ぐ。
2. **ノブ書き込みの再試行**: ノブスロットへの書き込みが失敗した場合、
   シーケンス全体を1回だけ再試行する（割り当ては冪等）。
3. **診断の可視化**:
   - 書き込み失敗時のトーストに、失敗した処理・段階・転送エラーを括弧付きで
     表示し、末尾にアプリログの場所も出す
     （例: `書き込みに失敗しました (write_key stage=save 4/4: write-failed) [log: …\monitor.log]`）。
   - GUI からの割り当て書き込みは、対象スロットを問わず、キー／メディア／
     マウスとも成否をアプリログに1行ずつ記録する
     （`write write_mouse keynum=13 layer=1 ok=false` の形式）。アプリ内部で
     失敗する書き込み（未知のアクション名など、本体へ何も送る前に止まるもの）
     も、アクション名つきで同じログに残る。
   - ノブスロットへの書き込みは、送信したフレーム列（16進）もあわせて
     `knob write …` 行に記録する。失敗した段階は `write failed: …` 行に残る。

アプリログの場所:

- 実行ファイル（`.exe`）と同じフォルダの `monitor.log`（例: ポータブル版なら
  exe の隣、インストーラー版ならインストール先フォルダ）。
- インストール先フォルダへ書き込めない場合（Program Files 配下など）は、
  従来の状態フォルダへ出力する:
  - Windows: `%APPDATA%\t1-keyboard\state\monitor.log`
  - macOS: `~/Library/Application Support/t1-keyboard/state/monitor.log`
  - Linux: `~/.local/state/t1-keyboard/monitor.log`
- 書き込み失敗時の表示には、実際に使われているログの場所が `[log: …]` として
  出るので、そちらが確実。

## 未検証

実機（T1 本体）でノブ割り当てが実際に反映されるかは未検証。上記で解消しない
場合は、アプリログの `write …` 行と `knob write …` 行（フレーム列と
ok=false の段階）が次の切り分け材料になる。
